## 1. 배경

온라인 쇼핑몰 "토토"는 주문·회계·운송을 사람이 수기로 옮기고 있어 누락과 지연이 잦다.
인스피언(EAI 회사) 개발자로서 이 흐름을 자동화하는 **API 기반 연계 시스템**을 설계·구현한다.
구체적인 설계와 구현 방식은 지원자가 정한다.

## 2. 연계 인터페이스

### 2.1 담당자 대화 (슬라이드 3)

인스피언 인터페이스 개발자 **김선임**이 묻고, ㈜토토 쇼핑몰 업무 담당 **최과장**이 답한다.

| 질문 (김선임) | 답변 (최과장) |
|---|---|
| 주문은 어떤 형식으로 들어오고, 어떻게 저장하나요? | XML로 받은 주문을 제가 쇼핑몰 DB에 입력해요. **주문 XML을 받을 API를 만들어 DB에 자동으로 저장**해 주세요. |
| 회계팀은 주문 정보를 어떤 형태로, 어디에서 받아 보나요? | 제가 **주문마다 영수증 파일을 만들어 FTP에 올리면** 회계팀이 가져가요. 이 작업을 자동으로 처리해 주세요. |
| 배송에 필요한 주문 정보는 언제, 어디로 전달해야 하나요? | 지금은 쇼핑몰 DB의 주문을 보고 운송회사 DB에 배송 정보를 넣어요. 이 작업이 **주기적으로 자동 처리**되게 해 주세요. |
| 장애가 나거나 데이터가 맞지 않을 때 확인해야 할 내용이 있나요? | **어떤 주문이 어디까지 처리됐고, 어느 단계에서 무엇이 잘못됐는지** 확인하고 싶어요. |

PPT 원문: 대화에서 필요한 업무를 파악하고 제공 환경을 활용해 프로그램을 개발한다. 구체적인 설계와 구현 방식은 지원자가 결정한다.

### 2.2 인터페이스 도출

위 대화에서 뽑은 업무 4가지. **트리거 열 중 굵게 표시하지 않은 값은 PPT에 명시되지 않은 해석이다.**

| # | 인터페이스 | 트리거 | 소스 → 타깃 | 설명 |
|---|---|---|---|---|
| IF-01 | 주문 수신 | 실시간 (REST 호출) | 주문 XML → `ORDER_TB` | 주문 XML을 받는 API를 만들어 쇼핑몰 DB에 자동 저장 |
| IF-02 | 영수증 전송 | 주문 저장 후 (시점 미명시) | `ORDER_TB` → FTP 파일 | 주문마다 영수증 파일을 만들어 FTP에 업로드 (회계팀이 가져감) |
| IF-03 | 배송 연계 | **주기 실행** (배치/스케줄러) | `ORDER_TB` → `SHIPMENT_TB` | 쇼핑몰 주문을 보고 운송회사 DB에 배송 정보 등록 |
| IF-04 | 처리 추적 | 전 구간 | — | 어떤 주문이 어디까지 처리됐고, 어느 단계에서 무엇이 잘못됐는지 확인 가능해야 함 |

## 3. 제공 환경

### 3.2 권한 제약

- **DB:** `SELECT`, `INSERT`, `UPDATE`만 가능 → `DELETE`·DDL 불가. 테이블 추가나 데이터 정리는 할 수 없음.
- **FTP:** 목록 조회와 신규 업로드만 가능. 다운로드·덮어쓰기·이름 변경·삭제 불가 → **파일명이 겹치면 안 됨**.
- **FTP 파일명:** 지원자 이름(한글) 포함 필수.

## 4. 접속 정보 수신 (선행 작업)

DB·FTP 접속 정보는 과제 API를 호출해서 받아야 한다.

1. **요청:** 과제 PPT 슬라이드 5의 URL로 HTTP Basic 인증(username/password는 PPT 참고) 호출.
   본문은 `NAME`, `PHONE_NUMBER`(`010-1234-5678` 형식), `E_MAIL`을 담은 JSON.
   PPT의 예시를 복사·붙여넣기하면 따옴표 글자가 깨지므로 직접 입력할 것.
2. **응답:**
   - `APPLICANT_KEY`: 지원자 키
   - `ORDER_TB_CONN`, `SHIPMENT_TB_CONN`, `FTP_CONN`: 암호화된 접속 정보
   - `SAMPLE_DATA`: Base64 인코딩된 **EUC-KR** XML 문자열 (주문 XML 샘플)
3. **복호화:** AES-128 / ECB / PKCS5Padding
   - Key = `SHA-1(휴대폰번호 문자열의 UTF-8 바이트)`의 앞 16바이트
   - 응답 문자열을 Base64 디코딩한 뒤 복호화

> 주의: 인증 정보와 복호화한 접속 정보는 Git에 올리지 않는다. 환경변수나 `.gitignore`된 설정 파일로 관리한다.

### 4.1 수신 결과 (2026-10-30 호출. 2026-10-31 재호출도 같은 응답, D-23)

결과 파일은 Git에서 제외된 `config/`에 있다 (`connection.json`, `raw-response.json`, `sample-order.xml`).

- **DB:** `ORDER_TB`와 `SHIPMENT_TB`가 같은 Oracle 인스턴스의 같은 계정에 있다. 다만 시나리오상 서로 다른 시스템이므로 DataSource는 둘로 나눈다 (D-02). 계정 이름으로 보아 **지원자 공용 계정**으로 추정 → 모든 조회·수정에 `APPLICANT_KEY` 조건이 반드시 필요.
- **FTP:** 업로드 경로가 지정되어 있다 (`connection.json` 참고). FTP와 FTPS 중 어느 쪽인지는 미확인.
- DB·FTP 실제 접속은 아직 확인하지 않았다.

### 4.2 샘플 주문 XML 분석

`SAMPLE_DATA`를 디코딩한 XML (EUC-KR). 이 세션에서 직접 파싱해 수치를 확인했다.

```xml
<HEADER>
    <USER_ID>USER01</USER_ID>
    <NAME>(주문자 이름)</NAME>
    <ADDRESS>(주소)</ADDRESS>
</HEADER>

<ITEM>
    <USER_ID>USER09</USER_ID>
    <ITEM_ID>ITEM45</ITEM_ID>
    <ITEM_NAME>(상품명)</ITEM_NAME>
    <PRICE>95000</PRICE>
</ITEM>
...
```

1. **올바른 XML 문서가 아니다.** XML 선언과 루트 요소 없이 `<HEADER>`와 `<ITEM>`이 나열되어 있다 → 루트 태그로 감싼 뒤 파싱해야 한다.
2. **HEADER와 ITEM은 위치가 아니라 `USER_ID`로 연결된다.** HEADER 바로 뒤의 ITEM이 다른 사용자의 것인 경우가 많다.
3. **규모:** HEADER 15건(`USER_ID` 중복 없음), ITEM 70건(`ITEM_ID` 중복 없음).
   - HEADER와 연결되는 ITEM: **63건**
   - HEADER가 없는 ITEM: **7건** (USER16~USER22) → `NAME`·`ADDRESS`를 채울 수 없음
   - ITEM이 없는 HEADER: **4건** (USER12~USER15)
4. **`ORDER_ID`가 XML에 없다** → 시스템이 채번해야 한다 (대문자 1자 + 숫자 3자리, 내 `APPLICANT_KEY` 범위 안에서 중복 없이).
5. `PRICE`는 모두 숫자이고 빈 값이 없다. 모든 값이 10자 이내.
6. `ORDER_TB`의 컬럼 구성(`USER_ID`, `ITEM_ID`, `NAME`, `ADDRESS`, `ITEM_NAME`, `PRICE`)으로 보아 **1행 = HEADER와 ITEM을 합친 주문 상품 1건**이다.
7. **해석: 샘플은 송신 메시지 규격이 아니라 샘플 데이터 묶음으로 본다.** 과제 API 응답(JSON)은 과제 정보를 전달하는 껍데기일 뿐이다. 그 안의 XML에도 여러 주문을 묶는 루트나 주문별 그룹(`<ORDER>`)이 없다. 묶음 전송을 의도한 규격이라면 이런 감싸기가 있었을 것이다. 따라서 실제 송신이 주문 한 건씩인지 여러 건인지는 알 수 없고, 수신 API는 둘 다 처리할 수 있어야 한다 (D-04, D-07).

## 5. 제출·면접 조건

- 화면 없는 일반 애플리케이션이면 됨. 필요한 라이브러리만 사용 (웹 앱 플랫폼 등은 불필요).
- **제출:** Git 저장소 주소를 채용 담당자에게 이메일로 제출. **작업 단위 커밋 내역 필요.** 마감일은 개별 공유. 기한 전에 끝내면 그때 면접을 볼 수 있다.
- **화상 면접(15분):** 제출 코드 이해도, 설계 역량 확인.
- **임원 면접:**
  - 현장 CBT 30분 (정보처리기사 난이도)
  - 과제 소개 PPT (발표 15분 이내)
  - 시연: 노트북에서 프로그램 실행, DB 접속 후 데이터 조회(참여자명·당일 날짜 기준), FTP 접속 후 업로드 파일 확인

## 6. 요구사항에서 나온 설계 쟁점과 결정

`D-xx`는 [decisions.md](decisions.md)의 결정 번호다. 결정이 반영된 설계는 [design.md](design.md)에 있다. 아래 항목은 모두 결정했고, 제공 환경을 확인해야 정할 수 있는 값은 [design.md §11](design.md#11-제공-환경-확인-후-정할-것)에 있다.

| 항목 | 내용 |
|---|---|
| 주문 XML 구조 | **확인됨 (§4.2).** HEADER + ITEM을 `USER_ID`로 조인해 `ORDER_TB` 1행 = 주문 상품 1건 |
| 짝이 없는 HEADER/ITEM | **결정 (D-07).** 온전한 주문만 저장, HEADER 없는 ITEM 7건은 거부, ITEM 없는 HEADER 4건은 경고. 모두 이력에 남김 |
| ORDER_ID 채번 | **XML에 없음 → 시스템 채번 확정.** `A001`~`Z999` 형식, APPLICANT_KEY 범위 안에서 중복 없이. 방식은 D-08 (H2 시퀀스) |
| SHIPMENT_ID 채번 | 시스템이 생성. 형식 동일. D-08 |
| STATUS 값 | ~~결정 (D-06): `RECEIVED` → `RECEIPT_SENT` → `SHIPPED`, 실패 `RECEIPT_FAILED`·`SHIPMENT_FAILED`~~ → **결정 (D-26).** 제공 DB에 CHECK 제약 `STATUS IN ('N', 'Y')`가 있다. `N` = 연계 진행 중, `Y` = 영수증·배송 모두 완료. 단계별 진행은 이력 DB(H2)에 둔다 |
| 영수증 파일 포맷 | PPT는 형식 자유, 파일명에 지원자 이름(한글) 포함 필수만 정함. **결정 (D-09):** 주문당 CSV, `영수증_{지원자명}_{ORDER_ID}.csv` |
| 처리 추적 방법 | DB에 테이블을 만들 수 없으므로 `ORDER_TB.STATUS`(연계 완료) + 이력 DB(H2, 단계별 진행)로 추적 (D-04, D-26). 조회 REST API에 H2만 바꾸는 운영자 재처리 API 하나를 더한다 (D-13, D-26) |
| 시연 시 "당일 날짜 기준 조회" | **해석 (D-11).** 면접 당일 시점에 `APPLICANT_KEY`로 내 데이터 전체를 조회한다는 뜻으로 봄. 제공 환경은 운영 환경으로 취급. 제공 DB에 PPT에 없던 `ORDER_TB.CREATE_TIME`·`SHIPMENT_TB.CREATE_DATE`(기본값 `SYSDATE`)가 있어 이 컬럼으로 조회하는 것으로 보인다. INSERT에서 빼 DB 시각이 들어가게 한다 (D-26) |
| 문자 인코딩 | **결정 (D-20).** 샘플 XML은 표시 없는 EUC-KR. 표시가 없으면 EUC-KR로 보고 MS949로 엄격 디코딩, 읽지 못하면 `400`. FTP 파일명(한글)은 UTF-8로 확인함 (D-09, design §11.1) |
| 트랜잭션·재처리 | **결정 (D-03, D-10).** 단계별 커밋 + 멱등성 + 사전 확인 후 재처리. 영수증과 배송은 따로 처리한다 (D-26). 건별 실패는 지수 백오프 5회 (D-22) |
| "웹 앱 플랫폼 불필요"와 IF-01 | IF-01은 REST API가 필요하므로 Spring Boot 내장 서버는 사용. UI는 만들지 않고 의존성은 최소로 |

## 7. 개발 환경

- Java 25, Spring Boot 4.1.2, Gradle Wrapper
- 현재 의존성: `spring-boot-starter-webmvc`, `spring-boot-starter-data-jpa`, QueryDSL(OpenFeign 포크), Oracle JDBC(`ojdbc17`) (D-01)
